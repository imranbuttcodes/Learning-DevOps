# ☁️ Amazon S3 

## 1. What is S3?

**Amazon S3 (Simple Storage Service)** is AWS's **object storage service**.

Its main purpose is to store files/data as **objects** inside **buckets**.

```text
AWS Account
    ↓
   S3
    ↓
 Bucket
    ↓
 ┌───────────────┐
 │ index.html    │
 │ image.png     │
 │ document.pdf  │
 │ video.mp4     │
 └───────────────┘
```

### Core distinction

> **EC2 = compute/run applications**
> **S3 = store files/objects**

---

# 2. Bucket

A **bucket** is a container for objects.

Example:

```text
demo-bucket-imran123
```

Inside it:

```text
demo-bucket-imran123
│
├── index.html
├── style.css
├── script.js
└── images/
    └── logo.png
```

Bucket names must be **globally unique** within S3.

Buckets belong to a specific **AWS Region**.

---

# 3. Object

Everything stored in S3 is an **object**.

For example:

```text
index.html
```

is an object.

An object consists broadly of:

```text
Object
├── Data
├── Key (name/path)
└── Metadata
```

Example:

```text
Key:
images/logo.png

Data:
actual image bytes

Metadata:
information about the object
```

---

# 4. Object Storage

S3 uses **object storage**, unlike EBS.

### S3

```text
S3
 ↓
Objects
 ↓
Files/data
```

### EBS

```text
EBS
 ↓
Blocks
 ↓
Filesystem
 ↓
EC2
```

So:

> **S3 = object storage**
> **EBS = block storage**

---

# 5. S3 Object URL

You uploaded:

```text
index.html
```

and AWS gave you a URL similar to:

```text
https://demo-bucket-imran123.s3.us-east-1.amazonaws.com/index.html
```

That is the **S3 object endpoint**.

However, your object was private, so simply having the URL doesn't necessarily give everyone access.

---

# 6. Pre-Signed URL 🔐

You discovered that AWS can generate a **pre-signed URL**.

It looked like:

```text
https://.../index.html?
X-Amz-Algorithm=...
X-Amz-Credential=...
X-Amz-Date=...
X-Amz-Expires=300
X-Amz-Signature=...
```

This URL provides **temporary authorized access** to a private object.

Your URL had:

```text
X-Amz-Expires=300
```

Therefore:

```text
300 seconds = 5 minutes
```

### Flow

```text
Private S3 Object
       ↓
AWS generates signed URL
       ↓
Send URL to someone
       ↓
They access the object
       ↓
S3 verifies signature
       ↓
✅ Access
       ↓
URL expires
```

Important:

> A pre-signed URL **does not make the object public permanently**.

# 7. Bucket Policies

S3 supports **bucket policies**, which are JSON-based resource policies controlling access to bucket resources.

Basic structure:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": "*",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::demo-bucket-imran123/*"
    }
  ]
}
```

We learned the important components:

### Effect

```text
Allow / Deny
```

### Principal

```text
Who?
```

For example:

```json
"Principal": "*"
```

means anyone.

### Action

```text
What can they do?
```

For example:

```json
"s3:GetObject"
```

means read/get an object.

### Resource

```text
Which AWS resource?
```

Our bucket:

```text
arn:aws:s3:::demo-bucket-imran123/*
```

The `/*` means **objects inside the bucket**.

# 9. Block Public Access 🚫

This was an important concept.

Even if you create a bucket policy saying:

```json
"Principal": "*"
```

S3 can still block that public access using **Block Public Access** settings.

Think:

```text
IAM permissions
      ↓
Can I modify the policy?
      ↓
Bucket Policy
      ↓
What access does the policy grant?
      ↓
Block Public Access
      ↓
Should AWS block public access?
```

So:

> **Bucket Policy and Block Public Access are separate mechanisms.**

For our public-access experiment, we had to disable the relevant Block Public Access settings.

For real production buckets, you generally want to keep public access blocked unless there's a deliberate reason to expose content.

# 10. Static Website Hosting 🌐

S3 can also host a **static website**.

Example bucket:

```text
my-website
│
├── index.html
├── style.css
├── script.js
└── images/
```

Enable **Static Website Hosting**, and S3 can serve those files as a website.

```text
Browser
   ↓
S3 Website Endpoint
   ↓
index.html
   ↓
Browser renders website
```

### Static means

S3 can serve:

* HTML ✅
* CSS ✅
* JavaScript ✅
* Images ✅
* Videos/files ✅

But it doesn't run server-side application code such as:

* FastAPI ❌
* Django ❌
* Express ❌
* PHP ❌

---

# 11. EC2 vs S3 Website Hosting

We specifically discussed this.

### EC2

```text
Internet
   ↓
EC2
   ↓
Apache / Nginx
   ↓
Website
```

EC2 gives you an actual virtual server where you can run:

* Apache
* Nginx
* FastAPI
* Node.js
* Docker
* etc.

### S3

```text
Internet
   ↓
S3
   ↓
Static website files
```

You don't manage an operating system or web server.

### Mental model

> **EC2:** "Give me a server; I'll run my application."

> **S3:** "Here are my files; store and serve them."

# 12. S3 + CloudFront

For a production static website, a common architecture is:

```text
User
  ↓
Route 53
  ↓
CloudFront
  ↓
S3
  ↓
HTML/CSS/JS
```

CloudFront can provide things such as **HTTPS, caching, and global edge delivery**.

# 13. S3 in an AI Backend

This is particularly important for your future AI applications.

Suppose a user uploads a PDF:

```text
User
 ↓
FastAPI
 ↓
S3
 ↓
PDF stored
 ↓
RAG processing
```

S3 can store:

* PDFs
* images
* user uploads
* documents
* datasets
* generated files
* backups

While:

```text
EC2 → runs FastAPI
S3  → stores files
RDS → stores structured database information
```

### The 7 things I'd make sure you remember

1. **S3 = object storage**
2. **Bucket = container for objects**
3. **Object = stored file/data**
4. **Pre-signed URL = temporary access to a private object**
5. **Bucket Policy = JSON-based access rules**
6. **Block Public Access = protection against unintended public access**
7. **S3 Static Website Hosting = serving static frontend files directly from S3**
